2. ESP32 HARDWARE INTEGRATION & DUAL-SOURCE HARMONY
--------------------------------------------------------------------------------
Problem:
  - The dashboard needed to support both software simulation and physical hardware,
    defaulting seamlessly to FastAPI/FastF1 streaming when hardware is absent,
    while automatically switching to ESP32 data when hardware is connected.
Solution:
  - Designed and authored full Dual-ESP32 architecture:
    * ESP32 #1: DAQ & Sensor Master (apex01_telemetry_master.ino):
        - Interfaces with physical GPS (UART), IMU (I2C MPU6050/BNO055), Hall-effect
          wheel speed sensor, and brake infrared temperature sensors.
        - Interfaces with SN65HVD230 CAN transceiver on GPIO 4/5.
        - Merges physical sensor inputs with CAN ECU frames.
        - Transmits telemetry packets via Wi-Fi HTTP POST or USB Serial JSON.
        - Gracefully falls back to simulated values if physical sensors or CAN are absent.
    * ESP32 #2: CAN ECU Simulator (apex01_ecu_simulator.ino):
        - Emulates vehicle engine management ECU over standard CAN bus at 500 kbps.
        - Broadcasts Standard CAN IDs (0x100: RPM/Throttle, 0x101: Speed/Gear/Brake,
          0x102: Engine/Coolant temps, 0x103: Battery Voltage/Current).
    * Bridge Program (bridge.py):
        - Created multi-mode telemetry ingestion bridge with 3 operation modes:
            1. Simulator mode (`--mode simulator`): default software streaming.
            2. USB Serial mode (`--mode serial --port COMx`): reads ESP32 via USB.
            3. Wi-Fi mode (`--mode wifi --esp-host http://...`): polls ESP32 via network.
        - Automatic data pipeline: Bridge -> FastAPI (`/telemetry/ingest`) -> WebSocket -> HUD.
  - Fail-safe Hierarchy:
    1. If ESP32 hardware is connected -> Ingest and display real sensor data.
    2. If ESP32 is disconnected -> Automatically stream FastAPI FastF1 telemetry.
    3. If backend network drops -> Client-side simulated fallback takes over immediately
       with zero frozen screens or UI crashes.

4. TELEMETRY INTEGRITY & GPS POSITION FIX (NO GLITCHING / JUMPING)
--------------------------------------------------------------------------------
Problem:
  - Car GPS marker on the track map was jumping forward and suddenly snapping
    backwards, and sensor values were desynchronized.
Root Cause Analysis:
  - Dual-Stream Race Condition: `useTelemetry.js` had an internal fallback timer
    running concurrently with the incoming WebSocket stream. Both loops were writing
    to the same state, causing track coordinates to alternate between different timestamps.
Solution:
  - Implemented Stream Arbiter (`lastExternalPacketMs` ref in `useTelemetry.js`):
    * Fallback loop checks timestamp on every tick. If a WebSocket packet was received
      within the last 2000 ms, the fallback loop immediately yields and sleeps.
  - Sanitized FastF1 Monza Dataset:
    * Cleaned coordinates in `api/monza_fastf1_telemetry.json` and `monza_fastf1_track.json`.
    * Enforced strict forward-only coordinate progression along the Monza racing line.
  - Strict Physical Correlation Guards:
    * Mutual throttle/brake exclusivity: when brake > 0, throttle is forced to 0%.
    * Gear-speed physics correlation (e.g. 8th gear on Rettifilo straight at 300+ km/h,
      downshifting through 7-6-5-4-3-2 into Variante del Rettifilo).
    * Synchronized deceleration G-forces tied directly to heavy braking zones.

6. SMOOTH 20 HZ SUB-FRAME INTERPOLATION & CLIENT LERP SMOOTHING
--------------------------------------------------------------------------------
Problem:
  - Discrete 10 Hz telemetry updates produced noticeable stepping on gauges,
    bars, and track position.
Solution:
  - Backend Sub-frame Interpolator (`api/index.py`):
    * Stepped streaming frequency from 10 Hz to 20 Hz (50 ms frame duration).
    * Created `get_interpolated_frame(idx_float)`: Performs linear interpolation (lerp)
      between consecutive FastF1 frames for all scalar fields and coordinates.
    * Average positional step reduced from ~3.5–17.8 px to smooth sub-pixel deltas (~1.6 px).
  - Client-Side Exponential Smoothing (`useTelemetry.js`):
    * Filter incoming frames with `smoothedFrame` ref:
        `smoothed = current + alpha * (target - current)`
    * Fast dynamics ($\alpha = 0.40$): Speed, RPM, Throttle, Brake pressure.
    * Position & Inertia ($\alpha = 0.20$): Track X/Y coordinates, Lateral/Long G, Brake temps.
    * Upgraded client-side fallback simulation loop to 20 Hz sub-frame interpolation.
    * Expanded rolling history buffer from 150 to 300 points for silky smooth line charts.
  - CSS Transition Tuning across UI Components:
    * `SuperbikeCluster.jsx`: Tachometer arc and throttle/brake mini bars upgraded to
      `duration-200 ease-out`.
    * `MonzaMap.jsx`: Live car beacon `<g>` transform upgraded to `duration-200 ease-linear`.
    * `F1Gauge.jsx`: Semicircular SVG gauge arcs upgraded to `duration-200 ease-out`.
    * `Powertrain.jsx`: G-Force traction friction circle dot upgraded to `duration-200 ease-out`.
